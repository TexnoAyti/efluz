# UZEFLIFE round advance and response time — 2026-11-05

Production inspection found round 1 still active with 28 of 121 results confirmed. The next-round action required every result, and its rejection message was hidden inside the admin screen.

The league admin button now submits the viewed round. It can open the following round with postponed matches still outstanding; a stale or concurrent retry returns 409 instead of skipping a second round. Existing scores, proposals, disputes and deadlines are retained. Previous opened league rounds remain reportable in the Mini App, and existing Telegram approvals stay valid when the active round changes; future public result actions and incomplete knockout progression stay blocked. The admin screen displays the current round, unfinished count, errors and successful round-opening notice.

Mutations return the state they committed instead of fetching the entire championship again. Result actions reuse their identity/subscription preflight state. A private invoker RPC reads plain championship JSON and the namespace generation together in one MVCC snapshot. The document adapter retains the existing generation CAS and rejects malformed snapshots before any write. Overlapping championship reads coalesce only while in flight; no completed result or authorization account is cached.

Database EXPLAIN execution was 154.375 ms versus 16.116 ms in separate probes. These are payload/database measurements, not a guarantee of complete phone request latency.

New-round opponent notices remain atomic with the round update and use the established in-app/Telegram pipeline. UZEFLIFE outbox processing now runs before other competition preparations consume its invocation budget. The existing ten-minute recovery schedule remains enabled. Delivery requires a linked Telegram account and a bot chat that Telegram permits messaging; imported usernames alone cannot receive private Telegram messages.
